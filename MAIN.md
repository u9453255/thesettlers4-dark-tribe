## In-place construction repair - 0.2.14

2026-10-12. The user reports Dark buildings still cannot be built in 0.2.13. The PID 23844 log shows every Temple/Fortress/Hall job paid, cancelled with mode 1 and refunded after timeout with `BUILD_BLOCK reason=ground entity`: units (e.g. entity 1206 at three different sites) walked into the cleared footprint before conversion. Farms worked because their footprint is small. This lifecycle defect, not the flag check, is confirmed by the log.

Successful construction no longer deletes or recreates anything. On payment the mod freezes the native CBuildingSiteRole at phase 1 (the tick dispatches only 2..8), detaches ordinary levelling/builder requests (slot 11) for Temple/Fortress, and applies the native reservation (RVA 0x136470) once, skipped when native phases already did it. Mana funds 30 ticks of native progress drawing. Completion mirrors native code: Farm/Hall use the builder-free grow path's phase-8 sequence (entity map anchor, flag 0x2000000, RVA 0x1362F0); Temple/Fortress use the native phase-5 pair RVA 0x1424C0/0x1429F0 when an ordinary economy exists, otherwise the same pile removal (CBuilding slot 16, delete mode 0) plus the phase-8 sequence. Units on the solid shape are waited for as native phase 7 does, with no timeout refund. Static blockers, lost sites or a refused start refund once and cancel with mode 1. Old 0.2.13-style paid conversions are refunded once and never recreated.

**Field fix (same version, rebuilt DLL).** User run PID 31592: three Farms were paid, started growing and were cancelled/refunded at the completion check as "static obstruction" (the logged reason was taken after cancellation, so it read "site identity"). Cause, confirmed by disassembly but not by a live reading of the flag: the completion check re-tested the placement flag bits on the site's own reserved cells. The object routine RVA 0x163510 (used when e.g. a Mushroom Farmer plants a mushroom) sets keep-clear bit 0x40 in a ring around each new object, so a mushroom next to the growing Farm failed the check. Native phase 7 checks only entity occupancy. Reserved cells are now checked the same way. Non-entity map values wait instead of refunding, and GROW_BLOCK records the reason at the decision. Startup log marker: `...completion verified; reserved cells checked for occupancy only`.

**Field fix r3 (PID 1696, same version).** The user reports construction mostly works, but there is periodic lag, some green markers still demolish instantly, Fortress never builds, and units moved to a landed Manacopter do not board.
- *Instant demolish:* the log shows start refusals with "terrain or static flags" (every Fortress and Temple) and "ground object" (some Farms and Halls). The native ordinary-site init edits its own cells (terrain 0x1C and claim bit 8; stakes through RVA 0x163940/0x163510 set bits 2/0x40). The start check repeated the placement flag test against those edits. It no longer repeats it, because the native validator accepted the click. Only another building on the solid cells is a hard blocker; any other entity is waited for. A redundant "unknown building within 32 tiles" refusal was removed.
- *Lag:* every pointer check was a `VirtualQuery` syscall. Whole-table scans cost tens of thousands of syscalls per tick (offline: 65,536 checks take about 40 ms). A per-tick, tick-thread-only region cache (`native/fast-memory.hpp`) is invalidated after every native/API mutation. The new memory fixture measures 524,288 cached checks at about 1.4 ms. The render/mouse threads are never cached.
- *Boarding:* aircraft clicks relied on sprite blits, which the HD renderer does not deliver. A unit move order targeting within 4 tiles of a landed aircraft now queues the same native boarding. BOARD_ORDER, BOARD_QUEUE, BOARD_CALL and BOARD_REFUSED log each step.
Startup marker: `...occupancy only; tick read cache r3`.

**Field round r5 (PIDs 35540/31724, same version).** The user reports four problems: clicking a growing building crashes; a Manacopter can only be picked while the Hall is selected and shows no selection marker; boarded units stay on the map (duplicates); terrain stays black around the aircraft.

Both are in the native site panel (slot 22, RVA 0x143D10). That panel reads the ordinary economy at the site entrance for the inhabitant (+0x1DE) and for each material pile (+0x1B0/2/4). Dark land has no such economy, so the pointer is null. The "pause construction" path (slot 8, RVA 0x142CCE to 0xD5B70) has the same flaw. Fix: at payment, the Temple/Fortress piles are removed (native removal steps) and their slots zeroed. Each growing site's role uses a per-kind copy of the building info with +0x1DE/+0x1DF cleared; this is re-applied every tick, including after a load. - *Boarding duplicates:* native boarding is the military-role arrival handler (slot 10, job state 24, RVA 0x189CD3). It sets mode +0x42 = 0xA and removes the unit from the per-tick scheduler (RVA 0x16D720, bucket +0x30) before calling RVA 0x16B890. The mod called only 0x16B890, so units kept walking and drawing. Passengers boarded by older builds are normalised before unload (`PASSENGER_NORMALISED`).
- *Terrain sight:* terrain fog is a separate per-cell byte map in the fog manager (RVA 0x1159D30, map at +0xC, low 3 bits = fog). Every 5 ticks each Manacopter reveals still-fogged cells within 15 tiles through the native cell reveal (vtable slot 7, RVA 0x1AED30), which also smooths edges. Slot 15 (RVA 0x1AEEF0) is deliberately not used: it appends persistent entries that are saved.

**Field round r6 (same version).** The user reports that the area a Manacopter flew over stays visible forever, with black blocks inside it (screenshot). Cause: r5 used two persistent writes. One was the fog manager's cell reveal (slot 7), which sets the current level directly. The other cleared the land byte-3 fog bits around the aircraft, which forced objects visible and disagreed with the terrain fog, hence the black blocks. Native vision works differently. Each fog cycle, the band pass (RVA 0x1AE210) calls RVA 0x1AE100(x, y, radius) for allied settlers (radius 25) and buildings. That writes pending bits 3-5 with a 6-ring soft edge, and the merge (RVA 0x1AE3F0) turns them into visible terrain and objects (land byte 3) and lets them fade when no longer refreshed. Aircraft (class 0x40) are outside the band pass's class table. The mod now calls RVA 0x1AE100 for each locally owned Manacopter every tick (radius 25) and removed both persistent writes. Cells already revealed in an existing save may stay revealed until the cycle overwrites them; a new map gives a clean check. Startup marker: `...; native temporary aircraft vision r6`.

**Field round r8 (same version).** The user confirms r7 works, but a selected Manacopter shows no selection bracket like units have. Native analysis: units get their bracket from their own draw method (CSettler slot 5, RVA 0x181370). When flag 0x200 is set, it fills the marker fields of the global draw descriptor (0x129ADFC..). The renderer then emits the marker (handler RVA 0x261B90, marker buffer at RVA 0x105A5E0). The Manacopter's slot 5 is an empty stub and its draw path never fills those fields, so no entity flag can produce the native bracket. Bit 0x400 was also tried. It is "show in GUI info panel" (Cart/Settler/Ship code calls virtual +0x94, which the 31-slot Manacopter vtable lacks), so it is deliberately not set; only 0x200 is mirrored. The mod now draws a native-style bracket (white corners, green bar) above each picked aircraft:
- On ticks, the screen position is solved by inverting the pinned projection (RVA 0x259910, which includes terrain height) and offset by the aircraft's sprite offsets +0x78/+0x7C.
- Under HD, up to 12 click-through, non-activating layered owned windows show it from the cached snapshot. Panel redraws ignore marker motion.
- On the classic renderer, GDI draws it on the frame surface.
Positions follow game ticks (about 10/s). The bracket's exact height above the sprite is an estimate to be confirmed in game. Startup marker: `...; aircraft selection marker r8`.

**Round r23 (0.2.15): placement markers on newly darkened land - investigation and diagnostics.** User report: on land that was taken and then turned into Dark land, building markers often do not appear (flaky). Static facts (pinned executable, file-only):
- Darkening a cell (RVA 0xCBB60) sets construction-flag bit 4 (flags map, pointer RVA 0x11630D8) and, through 0x25B210 -> 0x26D500, landscape byte 2 bit 0x40 together (bit 0x40 only when terrain > 7, i.e. not water); un-darkening clears both. The landscape pointer the hint scan reads (RVA 0xD69220) is the same array as the validator's (0x11630D4): both are set from it at RVA 0x114B90. So the scan's Dark pre-filter matches the validator's Dark notion.
- The Dark branch of the validator (0x13EBC0, reached from 0x13E4E0 for the Dark race) checks on every body cell `(flags & 0x5F) == 4` and an accepted terrain, then the slope (0x13DC90). It has no territory/owner test (the owner test at 0x13E62D/0x13E92A is in the other races' branches). The native cursor (0xEDF96/0xEDFFE) uses the same validator; the native background scan (0xEE3F1/0xEE602) only adds valid markers in owned 16x16 chunks and never removes ours.
- Conclusion: the mod's viewport scan applies exactly the native rules; on newly darkened natural ground the most likely rejecting causes are blocker bits in the flags (objects such as plants/trees and their keep-clear rings) or slope, which change while plants grow (hence flaky), whereas the starting Dark area was prepared by the scenario generator. Not proven at runtime.
- Added: `PLACEMENT_SCAN kind= view= darkAnchors= valid= anchorFlags= (bits 01/02/04missing/08/10/40) terrain= footprintOrSlope=` once per completed pass (at most every 5 s, only when it changes) while a Dark building is being placed. It identifies the rejecting rule for the user's next reproduction. No behaviour change.
Startup marker: `...; placement scan diagnostics r23`.
