## Confirmed file/source facts and interpretation

The original frame callback draws custom menus through IDirectDrawSurface7::GetDC. The HD Manager's managed Draw method selects its own DX11 render state for the HD in-game path. Its DX11RenderState creates a swapchain with IsWindowed=true and presents that chain. Executable/API file compatibility from 0.2.10 therefore did not establish that legacy surface drawing would reach the HD display. Combined with the initialized economy and missing panel image, this identifies the display-backend mismatch. The exact frame ordering/GetDC result in the user's session was not instrumented; no gameplay effectiveness is claimed.

## Display and input implementation

native/hd-overlay.hpp creates a process-owned WS_EX_LAYERED, WS_EX_NOACTIVATE, WS_EX_TOOLWINDOW popup attached to the game client. Its shared GDI panel bitmap is composed through UpdateLayeredWindow with black color-key transparency. The pane and the construction/aircraft tabs are drawn; the minimap/map and other transparent regions remain outside its input area. It never activates on clicks and it hides when the owner is minimized, loses foreground focus, leaves the matched scenario or HD video playback blocks input. This uses the standard [Windows layered-window mechanism](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features#layered-windows) and [non-activating window style](https://learn.microsoft.com/en-us/windows/win32/winmsg/extended-window-styles).

The canonical 200x600 canvas scales using the owner window's DPI and available client height. The same Geometry converts physical mouse coordinates back into canonical hit coordinates. A client height below 600 is unsupported; no global/process DPI setting or registry entry is changed. A hidden original window fixture checks 100/125/150/200 percent mapping, height clamping, actual layered drawing, ownership/styles, transparency, disabled clicks and WM_MOUSEACTIVATE. The engine's DX11 presentation and real overlay z-order/focus are still user acceptance.

Scene/build-menu state is cached on ticks. Both display backends read snapshots using TryAcquireSRWLockShared. HD panel clicks enqueue the same commands as the native panel; current mana, selection identities, queues and gameplay mutation remain validated on ticks. The overlay thread never calls Lua/game APIs or reads native entity pointers. The frame callback does not draw to the obsolete surface while HD is active; it resumes the native path when HD is off. Native sprite selection/flight/boarding and separate passenger UI are retained. Startup readiness requires panel-window creation, with a bounded wait only in the DLL startup worker. Diagnostic tick values are atomic for the added UI thread.
